# 头耦合透视：屏幕里的小空间

主人 2026-11-24 的构想：Sion 用摄像头找到主人的头，转头看过去。屏幕里的鲸鱼娘不是贴在屏幕上的正脸，而是住在一个小的 3D 空间里。主人往右走，就看到她的右脸；她也可以回过头来看主人。DSH 因此有了一个能自己支配、自己建模的空间。

这一页先讲清楚画面由哪些量决定，再比较几种做法，选出现在最可行的一种，最后列出分几步做、每一步怎么验证。它不是固定的流水线：身体只提供帧库这类原始能力，什么时候用、怎么用，由 DSH 自己决定。

## 画面由什么决定

把屏幕当成一扇窗，窗后面是一个固定在头里的小鱼缸，她在鱼缸里。主人从哪里看、她朝哪边，决定窗里看到什么。

| 量 | 含义 | 谁知道 |
|---|---|---|
| `head_yaw` / `head_pitch` | 头（也就是窗）在房间里的朝向 | Mac：舵机目标是 Mac 发的；也能读回 |
| 主人相对窗的方向 α | 主人偏离屏幕法线的角度，以及大致距离 | 摄像头在头里：主人的脸偏离照片中心多少，就是 α。头正对主人时 α≈0 |
| 她的朝向 ψ | 她在鱼缸里转向哪边（相对于窗） | DSH 决定 |

两种典型情况：

- **头跟着主人转（摄像头追踪）。** α≈0，窗总是正对主人。主人走到右边，头转过去，她如果「留在房间里原来的朝向」，相对窗就转了 ψ = −head_yaw，主人看到的就是她的侧脸。她想回头看主人，就让 ψ 回到 0。这就是主人描述的效果，只需要一个变量 ψ。
- **主人不动，头转开。** α = head_yaw，主人斜着看窗。按鱼缸视角（off-axis 投影）渲染，窗里的东西看起来像真实的立体物体。这是验证「立体感」最直接的测试，不需要摄像头。

所以帧库按 (ψ, α) 两个角度建索引就够了；多数时候只用 ψ 一维。

## 几种做法

| 做法 | 结论 | 理由 |
|---|---|---|
| A. 设备上实时渲染 3D | 不做 | ESP32-S3 没有 GPU；整屏 320×240 的 LVGL 刷新本身就要几十毫秒，再加光栅化做不到流畅。也违背「身体要薄」 |
| B. Mac 每帧渲染，实时推整屏画面 | 不做 | 实测一整屏 150 KB 要 1.7–1.8 s 才传完（v73），只适合静态图 |
| **C. Mac 预渲染，存进设备帧库；运行时 Mac 只发「显示第几帧」** | **采用** | 一条显示命令只有几十字节，v72 实测文字类命令往返约 27 ms；头的实时目标（`servo_setpoint`）也已经由 Mac 发，Mac 同时知道头在哪、该显示哪一帧，可以在同一条时间线上一起发 |
| D. 设备本地按舵机角度自动选帧 | 先不做，作为备选 | 只有 C 的实测延迟不够时才需要。它会让设备多一份「角度→帧」的规则，按分层原则这属于上层决定，能不放就不放 |
| E. 分层视差（几张透明层按角度平移） | 以后可选 | 省内存、能连续变化，但要把她的画拆成有深度的层；LVGL 叠多层透明图会更慢。可以作为 C 里帧的一种生成方式 |

**选 C 的原因。** 慢的东西（渲染、传图）只在加载时做一次；快的东西（换帧）每次只有一条小命令。头的运动和换帧都由 Mac 的同一条时间线发出，天然同步。设备只多一个「存帧、按编号显示」的原始能力，符合「身体只交机能」。

## 第 0 层：帧库（设备）

| 项 | 设计 |
|---|---|
| 存储 | 设备 PSRAM。v67 实测 PSRAM 空闲约 7 MB。帧库总预算 4 MiB（约 27 张整屏），另外每次分配后至少留 1.5 MiB 空闲给相机和其他功能，不够就拒绝，不会把内存吃光 |
| 编号 | 槽位 0–47。每张帧有自己的大小和位置（x, y, w, h），可以只覆盖屏幕的一部分 |
| 标签 | Mac 给每张帧附 16 位十六进制的内容标签（内容和位置的摘要）。重连以后 Mac 先列出帧库，标签一样就不用重传 |
| 生命周期 | 帧库只是内存，不占硬件。Stop、断线、离开脸页只会把画面从屏幕上撤下，帧还在；设备重启后清空。Mac 可以删单张或全部 |
| 显示 | 和现在的图片一样，只在脸页显示，盖在脸上，有显示时长（100–60000 ms）。换帧不复制像素，直接显示帧库里的那块内存 |
| 保护 | 只防损坏：预算上限、空闲内存下限；正在显示的帧被删或被覆盖前先撤下画面，不会显示已经释放的内存 |

协议（新增；hello 里声明 `frames:1`）：

| Mac → 设备 | 设备回复 | 说明 |
|---|---|---|
| `frame_begin {request_id, slot, width, height, x, y, tag}` | `display_result ready / no-room / invalid` | 开始往某个槽写一张帧；旧内容先删掉。不改变屏幕 |
| `image_chunk`（沿用） | `image_ack`（沿用流控） | 像素数据，RGB565 小端 |
| `image_end`（沿用） | `display_result stored / incomplete` | 写完，存入帧库 |
| `frame_show {request_id, slot, duration_ms}` | `display_result shown / no-frame / unavailable` | 显示一张帧。`unavailable` 表示现在不在脸页 |
| `frame_drop {request_id, slot}`（slot 为 `all` 时删全部） | `display_result dropped` | 删除 |
| `frame_list {request_id}` | `frame_list {request_id, used, budget, frames:[{slot,width,height,x,y,tag}]}` | 列出帧库 |

## 第 1 层：Mac 插件

- `stackchan_frame_store`：把一张图片（任何 macOS 能打开的格式）存进某个槽。标签由内容算出；同一个槽里已经是同样的内容就直接返回 `already`，不重传。
- `stackchan_frame_show` / `stackchan_frame_drop` / `stackchan_frame_list`：显示、删除、列出。
- `stackchan_servo_stream` 的每个时间点可以带 `frame`：同一条时间线里同时发头的目标和要显示的帧。也可以只有帧没有头的目标，用来播放一段帧动画。
- 直测驱动 `scripts/body_probe.mjs` 增加对应步骤，用来测速度。

这些都只是原样的能力。「主人在哪就把头转过去」「她什么时候回头看主人」属于第 2–3 层，由 DSH 的技能和意图决定，本仓库不写死。

## 画面从哪里来

| 阶段 | 内容 | 状态 |
|---|---|---|
| 1. 测试场景 | Mac 上用脚本光线投射渲染一个小鱼缸：有网格的缸壁、沙底、气泡和一条简单的鲸鱼（几个椭球拼成，能看出头尾和侧面）。按 (ψ, α) 渲染成一组帧 | 本次实现，用来验证帧库、速度和立体感 |

## 摄像头追踪（下一阶段）

摄像头在头里，随头转动。主人的脸在照片里偏离中心多少，就是 α；把头转过去让 α 回到 0，就是「找到主人的头看向他」。人脸检测放在 Mac（macOS Vision 框架很快），设备只拍照传图。现在的连拍是 640×480 JPEG、间隔至少 300 ms，传输速度决定追踪频率。要实测：每秒能拿到几张照片、从拍到转头的延迟。如果太慢，再考虑设备只传低分辨率灰度小图。

## 实测（v75 真机，2026-11-25）

- **立体感成立。** 主人坐在正前方，头在 ±30° 之间来回转，鲸鱼留在缸里不动（ψ=0）。主人说「像真的小空间」。同样的设置下如果让鲸鱼一直转过来正对主人，主人只看到缸和泡泡在变，觉得「鱼没变」。所以默认应该让她留在空间里，回头看主人是 DSH 自己决定的动作。
- **速度。** 存一张整屏帧约 1.7 s；换一帧往返约 27–33 ms。头的 400 个实时目标和 33 次换帧放在同一条时间线上，全部按时执行，最多迟到约 40 ms。
- **上限。** 整屏帧每秒 10 帧没问题，主人看着流畅。每秒 20 帧以上会断开：LVGL 重画时一直占着显示锁，会话循环拿不到锁，麦克风输入队列溢出。设备 RTC 记录到 `AudioError 4`。
- **保留。** 帧在断线后仍在。
- 详细数据见 [验收记录](validation.md)。

## v76：帧直接推给屏幕

v75 的上限来自 LVGL：换一帧要整屏重画（绘制缓冲只有 20 行，约 70 ms），重画期间一直占着显示锁，而会话循环也要这把锁，结果麦克风队列溢出。v76 改成这样：

| 项 | 做法 |
|---|---|
| 推帧 | 一个独立任务（核 1，优先级 2）把帧按 24 行一段，拷进两块内部 DMA 缓冲（拷的时候顺便转成屏幕要的字节序），再交给 LCD。全程不拿显示锁，会话循环不会被卡住 |
| 与 LVGL 互斥 | 显示帧期间 LVGL 暂停绘制（关掉重绘登记，丢掉还没画的区域），并等它最后一次传输结束。撤下帧时恢复 LVGL 并整屏重画脸 |
| 新帧到达 | 任务只做最新的请求（后来的覆盖还没开始的） |
| 传输完成 | 屏幕的传输完成回调分得清哪些是这些段、哪些是 LVGL 的，不会误报 LVGL 已刷完 |
| 理论上限 | 整屏 153,600 字节，SPI 40 MHz 约 31 ms，也就是每秒约 30 帧；小一点的帧按面积更快 |
| 协议 | hello 声明 `frames:2`；Mac 对 v2 按每张整屏 34 ms 留间隔，v1 仍是 100 ms |
| 代价 | 帧只盖住一部分屏幕时，帧外的脸在显示帧期间不动 |
| 真机（v76） | 每秒 20、30 帧都不断线。同样转速下，每步 5° 比每步 10° 明显更顺（主人确认）。见 [验收记录](validation.md) |
