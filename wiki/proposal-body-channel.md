# 方案：StackChan 作为 DSH 的身体（channel 化、可打断对话、开放接口、用量统计）

2026-11-22 · 方向已定，P1 进行中（2026-11-22 修订：按「给她一个身体」重写目标，取消夜间限制，语音回到主会话）。依据：v63 真机试装、[DSH 插件接口调研](#附录-a-dsh-插件接口事实)、[OpenClaw 调研](#附录-b-openclaw-可借鉴的做法)、语音会话的实际用量数据。

## 一句话目标

爹的原意：**这里做的是给 DSH 里的她一个身体，目标不是一个好用的桌面助手。**她在任何会话里都是同一个她，都能用这个身体；爹也应该随时能通过它找到她。

StackChan 是 DSH 的身体：它把**能做的事（能力）**和**身上发生的事（事件）**完整、随时可用地交给 DSH；DSH 用一份说明书知道怎么用，**自己决定**什么时候看、说、动、亮灯。插件里现在写死的规则（灯条怎么亮、何时转头、表情怎么换）只作为默认值，DSH 可以覆盖，也可以把自己喜欢的方式固定下来。

## 现状：哪些地方卡住了

| 问题 | 原因（已核实） |
|---|---|
| 别的会话（如 TG）用不了机器人 | 插件把设备绑死在一个「选定会话」上，工具调用时比对 `agent.id === preferences.sessionId`，不一致就报 `capability_session_mismatch`（`src/voice-runtime.mjs` 465/500/510/553/565 行）。**这是我们自己加的限制，DSH 本身允许全局工具。** |
| 问话和回答越堆越多 | 桥接是排队模型：你说的每句都进队列送给 DSH，每个回复都完整播完；没有打断，也不作废过时的回复。 |
| 规则写死 | 灯条状态、待机转头、按活动换表情都由插件决定，DSH 只能调用少数固定工具（6 个）。 |
| 回复慢、成本高 | 语音会话每说一句短话都要重新读入约 **17 万 token** 的上下文（走缓存）。这个会话 73 轮共读缓存约 **1,019 万 token**，输出只有 **2.9 万**。v63 里识别完到开口 3.6–4.7 秒，主要花在 DSH 生成。 |
| 试装要关桌面版 | 只是试装流程：换插件版本时桌面版要放开配置目录，另外我用无界面宿主拿日志。日常使用不需要关。 |
| 设备侧小问题 | Wake（挂机）默认关；在设置页改权限会断开对话；打开 Motion 后舵机打不开（`motion-open`）；会念出漏出的工具标记；短句会被识别成俄语。 |

## 设计原则

1. **身体和大脑分开**（沿用 [分离式设计](split-design.md)）。设备只做感知、执行和安全；判断、记忆、人格都在 DSH。
2. **能力完整、可达、有版本。** 每种硬件能力都有对应工具，每种身体事件都能送到 DSH。缺什么在设备能力报告里说清楚（已有 `notExposed`）。
3. **默认行为可覆盖。** 现在的灯条、转头、表情规则保留为默认值，方便测试；DSH 可以关掉、改参数，或者完全自己来。
4. **安全闸门在设备上。** 设备设置里的 Microphone / Camera / Motion / Ring 开关是最终闸门，任何会话都绕不过去。敏感能力（摄像头、远程喊话）默认需要开关打开，DSH 只能请求不能强开。
5. **不替她做决定。**插件和说明书只陈述事实（能做什么、失败码是什么意思、会花多少），不写礼仪规则、时段限制或固定流程。什么时候能打扰、晚上要不要叫人，由爹直接告诉她，她记在自己的记忆里并自主判断；爹不想被找时关掉设备或关掉对应开关即可。这样也给主动对话等别的插件留出空间。
6. **学 OpenClaw 的节点模型**：设备声明自己有哪些能力和命令，agent 在任何会话里都能调用，结果和事件按统一格式回来。

└───────────────▲─────────────── USB ───────────────────────┘
                │ 能力命令 / 事件 / 音频
┌───────────────┴──── Mac：dsh-stackchan 插件 ──────────────┐
│ 身体服务：连接、能力仲裁（谁在用摄像头/舵机/喇叭）、事件策略   │
│ 语音层：识别、合成、打断、合并、朗读清洗（可拆成通用插件）     │
│ channel：语音对话进出某个会话；其他会话通过全局工具使用身体     │

└───────────────▲──────────────────────────────────────────┘
                │ 全局工具 · followup/inject · 技能说明书
┌───────────────┴──────────── DSH ─────────────────────────┐
│ 任何会话（语音、TG、定时任务……）都能看、说、动、亮灯          │
│ 自己决定何时主动找你；喜欢的做法存进自己的记忆               │
└──────────────────────────────────────────────────────────┘

### 1. 语音 channel

参照 dsh-im-connect（TG 等聊天软件的接入就是这样做的）：

- **进**：识别出的话用 `agent.followup(...)` 送进绑定的会话，来源标为 `source.kind: 'stackchan-voice'`，DSH 能分辨这句话是对着机器人说的。
- **出**：插件监听绑定会话的 `session/event` / `agent/assistant-stream`，把回复清洗后朗读；其他会话的回复不朗读，除非那个会话主动调用 `stackchan_say`。
- **绑定哪个会话可以配置**：默认一个固定的「家」会话；也可以说「切到 xx」或在设置里换。绑定关系存在插件状态里，不再写死在偏好里。
- 不再需要「选定会话才可用」：设备连上就可用，channel 只决定**语音对话**进哪个会话。

### 2. 全局工具 + 占用仲裁

- 工具在插件根上注册为**全局工具**，任何会话都看得到、调得到（DSH 原生支持）。
- 去掉会话比对，换成**占用规则**：摄像头、舵机、扬声器同一时间只给一个调用者；冲突时后来的排队或得到 `busy`，谁在用、从哪个会话来的都记进日志。
- 设备上的权限开关仍是最终闸门：关着就返回 `permission-disabled`，DSH 知道原因、可以请你打开。

### 3. 工具清单（目标）

| 工具 | 现在 | 目标 |
|---|---|---|
| `stackchan_device_status` | 有：能力、电量、光线/接近、头顶触摸、惯性 | 加权限状态、谁在占用、当前表情和灯效、是否有人说话 |
| `stackchan_say` | 有：说一段话 | 加音量（含紧急喊话，上限由你定）、是否等说完、可被打断与否 |
| `stackchan_take_photo` | 有：拍一张 | 加分辨率；连续拍几张 |
| `stackchan_move_head` | 有：转到某个角度 | 加点头/摇头等小动作；回中位 |
| `stackchan_set_expression` | 有：6 个基础表情 | 鲸鱼娘全部脸（盯着、害羞、思考、犯困……）+ 眨眼、动嘴等动作，持续时间 |
| `stackchan_light_ring` | 有：一种颜色亮一段时间 | 左右两条分别控制、逐颗颜色、渐变/流动/呼吸、持续到撤销 |
| `stackchan_listen` | 无 | 听一段（几秒）：返回音量、是否有人声、转写文字 |
| `stackchan_show` | 无 | 在屏幕上显示一行字或一张小图，一段时间后回到脸 |
| `stackchan_behavior` | 无 | 读/改默认行为：状态灯自动/关、待机转头开关和幅度、按活动换表情开关、事件推送策略 |

DSH 自己组合这些：比如「看看你在不在」= 转头 → 拍照 → 判断 → 必要时说话。插件**不提供**写死的「找人」流程，只在说明书里给示例。

### 4. 身体事件 → DSH

| 事件 | 例子 | 送达方式 |
|---|---|---|
| 摸头、点脸 | 被摸了、被戳了 | 可选：唤醒会话（`followup`）或只记入上下文不打扰（`inject`） |
| 有人靠近 / 离开 | 接近传感器变化 | 同上 |
| 被拿起、晃动 | 惯性数据 | 同上 |
| 电量低、充电状态变化 | | 同上 |
| 连接断开 / 恢复、权限被改 | | 只记入上下文 |

哪些事件推、多久最多推一次，由 DSH 通过 `stackchan_behavior` 自己设（现在是写死的 30 秒冷却、每小时 12 次）。

### 5. 主动联系

DSH 已有定时任务（`ctx.schedule`）和会话间发消息的能力。「TG 没回 → 用机器人看看你在不在 → 急了就喊话」这件事由她自己决定和执行，任何时段都可以；插件只保证工具在任何会话里随时可用。说明书不写打扰礼仪，爹的偏好（比如「晚上尽量别吵我」）由爹直接告诉她。

### 6. 说明书（技能）

用 `ctx.skills.register` 随插件附一份 `SKILL.md`：每个能力是什么、限制和权限、失败码含义、常见组合示例（找人、提醒、陪聊时的表情和灯）。DSH 读它就知道怎么用；你觉得好的做法，DSH 记进自己的记忆，下次照做。

## 对话改造（学 OpenClaw 的 Talk Mode）

| 做法 | 说明 |
|---|---|
| 半双工 | DSH 思考时不把新收音当新问题排队；你说话时她不抢话。 |
| 可打断 | 她说话时你开口：满足「至少几个字、不是她自己正在说的内容（防回声）、近 0.35 秒有能量」就立刻停播，并在下一轮提示里写明「在第 X 秒被打断」。StackChan 的喇叭离麦克风很近，防回声这一条最关键；设备上已有回声消除，先实测效果。 |
| 合并 | 静默超过一定时间（中文约 1.2–2 秒）才提交；连着说的几句合成一轮。 |
| 作废旧回复 | 每轮有编号，新一轮开始，旧回复（包括还没播的部分）一律丢弃。 |
| 朗读清洗 | 去 Markdown、代码、链接、表格，去掉漏出的工具调用标记；代码占大半时改说「详细内容我发到屏幕上了」；超长回复先摘要。 |
| 识别限定中英文 | 避免短句被识别成别的语言。 |
| 边生成边朗读 | 现在已做「第一句先播」；下一步按句子流式朗读。 |

这部分和机器人无关，可以拆成一个**通用的 DSH 语音对话插件**（Mac 本机麦克风也能用），StackChan 插件依赖它。新仓库按 project-wiki 规范维护（wiki、来源、验证记录、不放私人素材）；借鉴 OpenClaw 的部分保留其 MIT 版权声明。**推到 GitHub 公开之前先问你。**

## 用量与成本

**现状（本机实测数据）**：语音会话最近 20 轮，每轮新输入中位数约 390 token、输出约 195 token，但缓存读入中位数约 **17.2 万 token**。也就是说，花费和等待几乎都在「每说一句都把整个长会话再读一遍」。

**统计**：插件每轮记录来源（语音/TG/定时）、新输入/缓存读/缓存写/输出 token、DSH 生成耗时、识别和合成耗时；会话总量读 `sessionController.projections` 的 `tokenUsage`。价格沿用已装的 dsh-usage-stats 的价格表估算（DSH 本身只记 token 不记钱）。设置页加一张报表：按天、按来源、按会话，标出最贵的环节。

**优化方向（需要你选）**：
- **A. 语音专用短会话**：语音 channel 绑一个上下文很短的会话，只负责陪聊和身体；遇到需要长记忆或干活的事，转交给主会话（会话间 `followup`），结果再回来朗读。最省、最快。
- **B. 继续用主会话，但压缩上下文**：依赖已装的 dsh-context / billion-context 控制长度。保留完整记忆，但每轮仍然较重。

## 设备侧（固件）配合

- 设置页改权限不断开对话；权限变化实时上报给 Mac。
- 查清 `motion-open`（打开 Motion 后舵机仍打不开）。
- 新能力的固件命令：全部表情和动作、逐颗灯效、屏幕显示文字、音量。

## 已定（2026-11-22，用户：按建议来）

1. **语音进固定的「家」会话**：默认是现在选定的会话，可在设置里或用语音改。
2. **摄像头只看设备上的 Camera 开关**，不做每次确认；每次拍照设备上要有可见提示（表情或灯），并记日志（哪个会话、何时）。

5. **开源语音插件叫 `dsh-talk`**，做好后先给用户看，再决定是否公开。
6. **从 P1 开始**，按 P1 → P2 → P3 推进。

## 附录 A：DSH 插件接口事实

读的是本机 DSH 0.2.2-rc.5 和已装插件的代码（只读）。

- DSH 核心**没有**统一的 channel 接口；TG 等接入是 `@michengai/dsh-im-connect` 自己实现的（`src/engine/types.ts` 的 `ChannelAdapter`）。
- 进：`SessionRouter.getOrCreate` 按「渠道:私聊/群:聊天 id」找会话，新会话用 `ctx.agents.create`，旧会话 `ctx.agents.resume`，消息用 `agent.followup({ role:'user', source:{ kind } })` 送入。
- 出：全局监听 `session/event`、`agent/assistant-stream` 等，把绑定会话的回复转发出去；非用户发起的回合也能送达（主动消息）。
- 工具：`ctx.tools.register` 从插件根调用即**全局**；从会话作用域调用则只在该会话。执行上下文 `ToolRunContext` 带 `agent`（含 `followup/steer/inject`），没有来源渠道字段。
- 唤醒和注入：`followup`（排队并唤醒）、`steer`（下一步插入）、`inject`（只加上下文不唤醒）。定时：`ctx.interval`、`ctx.schedule`（after/at/every/cron……，只在 DSH 运行时生效）。
- 图片：`ctx.get('attachments').saveImage` → 工具结果里返回图片（我们现在的做法）。
- 用量：每步 `assistant/message.data.usage` 记 token（含缓存读写）；会话级 `tokenUsage` 投影；DSH 不记钱，dsh-usage-stats 用自己的价格表估算。
- 说明书：`ctx.skills.register({ name, description, content, resourceBase })`；常驻提示可用 `ctx.systemPrompt.section`。
- `dsh-speak-up` 没有语音合成，是「定时主动开口」的触发器；核心另有实验性的语音识别接口 `ctx.speechToText`。

## 附录 B：OpenClaw 可借鉴的做法

OpenClaw（MIT）。只读了公开文档和代码。

- **Talk Mode**（`apps/macos/Sources/OpenClaw/TalkModeRuntime.swift`）：静音超时才提交；思考时不收音，所以不会堆积；朗读时保持识别，满足「≥3 字、不是自己正在说的内容、近 0.35 秒有能量、置信度 >0.6」才打断，并记录打断位置写进下一轮提示。
- 机身扬声器场景下（没有回声消除）会关掉打断或在播放时静音麦克风——StackChan 要实测设备回声消除够不够。
- **朗读清洗**（`src/tts/speech-text.ts`、`src/shared/text/strip-markdown.ts`）：代码占一半以上就改说「详细内容在屏幕上」；其余去 Markdown、链接只留文字、表格转列表、压缩符号；超长先摘要。
- **队列模式**：steer / followup / collect（静默窗口合并）/ interrupt（只跑最新），默认 500 ms 防抖。实时语音里新任务取代旧任务，被取消的任务不读半截答案，用轮次编号丢弃迟到结果。
- **节点**：设备连上时声明 `caps`、`commands`、`permissions`；agent 在任意会话里 `node.invoke`；设备主动 `node.event`；敏感命令（摄像头、录屏）必须显式允许，拒绝优先。
- **主动联系**：定时任务（默认 30 分钟、仅空闲时、限活跃时段）在主会话或隔离会话里运行，结果发到指定渠道。没有「不回就换渠道找你」的现成功能。
- **用量**：`/usage tokens|full|cost`、按会话记录汇总，支持拉取 DeepSeek 余额。
- 现成的 ESP32 节点固件（esp-openclaw-node）需要刷固件，违反我们的约束，不用；做法是 Mac 侧代替机器人当「节点」，正是现在的结构。

## v64 实测与 v65（2026-11-22 下午）

- **堆积根因**：语音回合里 DSH 调 `stackchan_say`，`bridge.say` 排在 `this.queue` 上，而那个回合自己还占着队列——自己等自己，127 秒后设备睡下才 `dropped`；期间爹说的话全并进下一轮。修法：`src/bridge.mjs` 回合进行中（`turn.asking`）的 say 直接按 `turn.speaking` 顺序插播，最终回复等它播完。测试 `saying something from inside the voice turn plays now…`（旧代码超时）。
- **舵机根因**：用 openocd 暂停设备读 RTC trace（`sion_device_trace` @0x50000000，5992B，脚本 `work/active/v64-body/physical-v64.*/trace-openocd.cfg`），Boot lane 16 次 `MotionOpenFailed step=power-enable cause=enable-readback`。PY32 GPIO0（VM_EN）拉高后输入位仍读 0；官方 HAL（`hal_io_expander.cpp`）只写不读。`firmware/agent/motion_power.cc` Check 改为：高电平看 mode+输出锁存，低电平仍要求输入为低。真机是否真的上电要看 v65 下一步（若仍失败会落到 step 6 SCS，并带 MotionLimits）。
- **对话泡泡**：caption 协议升到 `caption:2`，新增 speaker `status`（只发给声明 2 的固件）。DSH 侧 `binding.ask({onProgress})` 从 assistant-stream 报思考/工具/正文；bridge 300ms 节流：开头「思考中…」，思考尾部 90 字、`正在用 <tool>…`、流式正文作为 assistant caption。固件 Whale 页底部白色圆角泡泡（304×66，不拦触摸），优先显示 status，否则回复，否则听到的话；取尾部 108 字节；status 30 秒、其余 12 秒无更新后隐藏。Whale 模式也加载 caption 字体并请求 caption。

## v65 实测（2026-11-22 晚）与 v66 待装

- **开源约束**：插件不写死任何个人或本机细节（唤醒名、会话、端口、名字）。代码只带通用默认值，个人值放在 profile 配置或本地适配层里。
- **唤醒名配置化**（插件，已热换）：`preferences.wakeNames` 是字符串数组，默认值是 `['stackchan','stack chan']`。写法规则：`[abc]` 表示任选其中一个字，`(ab|cd)` 表示几种写法任选一种，名字中间允许夹空格。识别器常把字写成同音字或繁体（实测出现过「小地帶嗎」「有地在嗎?」），这些变体由使用者自己列进配置。「在吗」部分的同音和繁体写法是通用的，所以留在代码里（`src/bridge.mjs` 的 `createWakeMatcher`）。没有匹配上的话语记为 stage `wake-unmatched`。
- **舵机 Fault 锁死整机**（固件，v66）：原来 `ready_to_connect()` 要求 `motion_idle()`，而 MotionEngine 一旦进入 Fault 只有重启才能退出，结果 USB 和 Connect 被静默忽略，对话结束时显示 「Release failed」。v66 改为：Fault 只把舵机自己锁住（`Begin` 仍然拒绝），`motion_idle()` 把 Fault 当作空闲，`ResourcesStopped` 把舵机 Failed 当作 Done，trace 里继续记录原始位。UI 测试 case 79 已按新语义修改，`scripts/test_agent.py` 通过。
- **泡泡**（固件，v66）：Whale 页忙碌期间（说话中、Waiting、Speaking）持续刷新泡泡，不再 12 秒后自动隐藏。
- **舵机根因**（未解决）：电源读回已经修好，现在卡在 `motion_scs.cc` 的 `DisableBoth()` 读回 torque 这一步。v66 要把 SCS 状态字节和错误码写进 trace，由固件自己报告，不再靠 JTAG halt 读取：select-once 待确认状态下 halt 会触发看门狗复位，设备会回落到原厂。
- **试装注意**：v65 是通过 select-once 进入的，没有被标记为有效。RST 或看门狗复位都会回到原厂，重新进入需要写回 0xd000 扇区。插件热换时，必须先关闭语音服务，再执行 install_bundle，并且同一路径的包会被判定为 already-installed，要换一个路径。
